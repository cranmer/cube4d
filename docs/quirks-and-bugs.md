# Quirks, bugs, and traps in the original

Things found while reading MagicCube4D that a port has to make an explicit decision about. Each entry
says what it is, where it lives, and what this project does about it.

These are **not complaints**. Most are deliberate engineering trade-offs in a program that has worked
reliably for twenty years, and several are documented in the source by the authors themselves. They
are recorded here because a reimplementation that silently "fixes" them can silently break
compatibility.

Line references are against the `magiccube4d/` submodule and were verified 2026-07-27.

---

## Load-bearing hacks

### The slicer cannot handle a vertex exactly on a cut plane

`CSG._slice`'s dimension-0 case throws `Unimplemented` if a vertex lies exactly on the cutting
hyperplane. Rather than handle the degenerate case, the construction **deliberately nudges cuts off
centre** so it can never arise:

```java
// PolytopePuzzleDescription.java:196-198
private final static double SLICE_MULTIPLIER = 0.99999;
private final static double SLICE_MULTIPLIER_SIMPLEX = 0.995; // Special case because too close to 1
                          // affecting drawing and too far from 1 was affecting grip detection.
private final static double SLIVER_VOLUME_PERCENT = 15; // Cull stickers with volumes < this % of average.
```

Even edge lengths would place two middle cuts at the same offset, so the thickness is scaled by
0.99999 and the resulting degenerate sliver stickers are culled by volume afterwards.

The source comment warns to re-run the module test if these are changed. The comment on
`SLICE_MULTIPLIER_SIMPLEX` is a small masterpiece of honesty: the value was squeezed between two
different failure modes.

**Decision:** irrelevant to us. Because geometry is generated by the original Java at build time,
these constants are applied by the code that has always applied them. A TypeScript reimplementation
would have had to replicate all three exactly — one of several reasons it was not chosen.

### Provenance is carried in a mutable `aux` field

Sticker-to-face and sticker-to-piece mappings are recoverable only because every element is stamped
with its index before slicing, and slicing preserves the stamp. A ridge whose `aux` survived came
from the original polytope rather than from a cut, which is how pieces are identified.

**Decision:** the exporter reads the results, so this stays internal to the Java. Any future
TypeScript CSG port must design an equivalent provenance mechanism from the start — retrofitting it
would be painful.

## Genuine bugs

### `length` is mutated inside the per-face cut loop

```java
// PolytopePuzzleDescription.java:454 and :478
length = ceilLength;
```

The `length` parameter is reassigned **inside** the loop that decides cut placement for each face.
Once any face trips a special case — simplex, tetrahedral prism, triangular-prism face, uniform
triangular duoprism, or a prism face — `length` stays clobbered for **every subsequent face in the
loop**. For fractional edge lengths, the resulting cut layout therefore depends on face iteration
order.

`this.edgeLength` is captured before the loop, so `getEdgeLength()` still reports the original value.
The effect is invisible unless you look for it.

**Decision:** not fixed, and deliberately so. Fixing it would change generated geometry and therefore
grip ordering, invalidating every existing save file. The build-time-export architecture is immune —
it runs the actual code. A future TypeScript CSG port would have to reproduce this bug-for-bug, which
is worth knowing before starting one.

### `{3,3}x{}` — the tetrahedral prism — does not build

```java
// MagicCube.java:55
//{"{3,3}x{}", "1,2,3,4,5,6,7",  "Tetrahedral Prism"}, // FIX: Simply fails.
```

Commented out of the catalog upstream. Never entered our Phase 0 survey, so we have no diagnosis
beyond the author's.

**Decision:** out of scope for v1. Worth revisiting later — a fix would be a real contribution back
upstream, not just to this port.

### The `c ` current-position marker never round-trips

`History.read` computes which node should become `current` as `last == null ? first : last.next`
(`History.java:620`), but `last.next` is always `null` at that point, so `current` always resolves to
end-of-list. Loading a log with a mid-list `c ` marker silently discards the position.

In practice it never manifests, because saving truncates the redo tail first (below) and so never
writes a mid-list `c `.

**Decision:** our parser handles `c ` correctly, and our writer emits it. Since the legacy reader
ignores position rather than erroring, files we write remain loadable by the original.

## Deliberate behaviours we are dropping

Both of these are choices, not bugs. Both are dropped from the core and available behind a
preference. Neither affects file compatibility.

### Appending a move that inverts the previous one erases both

```java
// History.java:254-272
if(node ... && node.dir == -dir)  // but in the *opposite* direction.
    undo();  // just back the move out rather than append an inverse move
```

Twist a face and immediately twist it back, and both moves vanish from the history — along with the
entire redo stack, since the cancellation calls `truncate()`. The displayed twist counter becomes
non-monotonic.

**Decision:** dropped. It silently destroys redo state and surprises users. It never affects what is
written to a file, so interop is unaffected either way.

**One genuine asymmetry remains and cannot be designed away:** the Java *reader* also applies this
cancellation (`History.java:615`). So a log containing an adjacent inverse pair loads into the Java
as a *different* move list than the one in the file. Our parser is faithful to the bytes and returns
a warning, rather than silently matching the Java or silently diverging from it.

### Saving destroys your redo stack

```java
// MC4DSwing.java:228
hist.truncate(); // Don't save potential redo moves after current. Note: loses redo moves as a side effect!
```

The comment acknowledges it. Saving discards everything after the current position, in memory as well
as on disk.

**Decision:** dropped. We save the full move list plus an index. This is **not** a format limitation
— the legacy grammar already supports a mid-list current position via the `c ` marker, the original
simply chose not to use it.

## Known-imperfect by the authors' own account

### Sticker → grip resolution

When you click a sticker, the program must decide which of the grips on that cell you meant. It uses
the piece's colour count: `gripDim = nDims − numColorsForCubie(piece)`, so a 4-colour corner maps to
a vertex grip, a 3-colour edge to an edge grip, and so on. Then it takes the nearest grip centre in
4D.

The source contains a 20-line admission that this is inadequate
(`PolytopePuzzleDescription.java:1163`+):

> There is a fundamental problem with the approach in this block, which is that the
> number-of-colors isn't a discriminating enough property to classify piece types. There will be
> situations on some puzzles where different piece types have the same number of colors (simplex
> puzzles), and situations where we want those different piece types to do different [things]…

**Decision:** v1 reproduces this behaviour exactly, and pins it with fixtures generated from the
Java, so it is captured as *behaviour* rather than left to drift.

The proper fix — marking piece-to-parent-element incidence at build time — is *easier* under this
project's architecture than under the original, because the exporter still holds the polytope object
and can emit incidence data as an extra block with no runtime cost. A promising future improvement.

### The 2×2×2-cell special case

`PipelineUtils.is2x2x2Cell` distinguishes a 2×2×2 cell by comparing squared distances against
hardcoded values with a tolerance:

```java
|‖stickerCenter − faceCenter‖² − 0.75| < 0.1  &&  |‖polyCenter − faceCenter‖² − 1.5| < 0.1
```

A geometric guess with magic numbers, needed because such a cell can be gripped by any of its faces.

**Decision:** reproduced as-is, pinned by fixtures.

### Two unimplemented pipeline stages

`PipelineUtils.java:213` and `:354` are both `// XXX DO ME?` — the 4D and 3D near-clip stages were
never written. In practice the default eye distances keep geometry safely in front of both eye
points.

**Decision:** not needed. A GPU pipeline gets proper clipping for free.

### Two unimplemented interface methods

`getGripInds()` and `computeGripVertsAtRest()` both `throw new RuntimeException("unimplemented")`.
Grips are picked by proximity to sticker and polygon centres, never by their own geometry.

**Decision:** dropped from the TypeScript interface entirely.

## Performance characteristics worth knowing

### Geometry is rebuilt every frame

The full per-vertex pipeline runs on the CPU on every repaint, even when nothing is moving. There is
a `// XXX probably doing this more than necessary` in `PuzzleManager`. For the largest puzzle that is
~65,000 vertices per frame in software.

**Decision:** the entire per-vertex pipeline moves into a vertex shader, reducing per-frame CPU work
to uploading a handful of uniforms.

### Twist permutations are recomputed from scratch every time

`applyTwistToState` re-derives the permutation geometrically — rotate each sticker centre, look it up
in a fuzzy hash — on every single call. No memoization anywhere.

**Decision:** memoize per `(grip, direction, slicemask)`. Roughly a 10× speedup when replaying a long
solve log, which the original does on every load since it never serializes state.

### Animation speed is frame-count based

A quarter turn is 11 frames × `twistfactor`, so animation speed depends on refresh rate. The speed is
also locked in when a move is dequeued, so adjusting the slider mid-move has no effect — flagged in
the source with `// XXX ARGH!`.

**Decision:** time-based animation driven by `requestAnimationFrame`, keeping the original's
`(sin((x−0.5)π)+1)/2` easing curve.

## Precision trap (ours, not theirs)

Not a bug in the original — a trap for anyone porting it.

`FuzzyPointHashTable` is constructed with **absolute** epsilons:

```java
// PolytopePuzzleDescription.java:366 and :672
new FuzzyPointHashTable(1e-9, 1e-8, 1./128)
```

The largest circumradius in the catalog is 31.87 (`{100}x{4}`), so a 1e-8 absolute tolerance is
**3.1e-10 relative** — roughly 380× finer than float32's ~1.2e-7 resolution.

Storing sticker centres, grip rotation bases, face normals, or cut offsets as float32 would cause
twist lookups to miss their hash bucket and throw — but only on large-coordinate puzzles, and only
for some grips. A textbook silent, data-dependent failure.

**Decision:** those four arrays are Float64 in the asset format, non-negotiable. Render-path data
stays Float32, where it is *bit-exact* with the Java (which already narrows to `float`). The
"every twist permutation is a bijection" property test is the canary: a single float32 leak fails it
immediately, naming the puzzle and the grip.
