# The `.mc4dpz` asset format

Every puzzle in MagicCube4D's catalog is generated by slicing a 4D polytope with hyperplanes — an
expensive computation that the original re-runs from scratch on every load. This project does that
work once, at build time, and ships the result. A `.mc4dpz` file is that result for one
(puzzle, edge length) pair.

Why this exists rather than a TypeScript port of the geometry engine is covered in
[`architecture-options.md`](architecture-options.md). This document is about the file itself.

---

## The problem it solves

A puzzle's geometry is about twenty arrays of numbers — sticker centres, face normals, grip rotation
matrices, polygon vertex indices, and so on. For the largest puzzle in the catalog that is roughly
400,000 numbers.

The obvious encoding is JSON. It is also the wrong one: as text, the largest puzzle is about 30 MB
and takes seconds to `JSON.parse`, and then you have JavaScript arrays of boxed numbers rather than
the compact buffers the GPU wants.

So the arrays are stored as **raw bytes**, exactly as they sit in memory. The file becomes:

```
┌──────────────┬─────────────────┬───────────────────────────────────┐
│ magic + ver  │ header (JSON)   │ blocks (raw bytes, back to back)  │
└──────────────┴─────────────────┴───────────────────────────────────┘
```

Loading is then `fetch` → `ArrayBuffer` → construct views. Nothing is copied and no numbers are
parsed. Decoding the largest puzzle costs about as much as the download.

---

## Blocks and the block table

**A block is one array.** `stickerCenters` is a block. `gripUsefulMats` is a block. They are written
one after another, with no separators — just bytes.

Raw bytes alone are unreadable, so the header carries a **block table**: a directory saying, for
each block, where it starts and how to interpret it.

```jsonc
{
  "schlafli": "{4,3,3}",
  "edgeLength": 3,
  "nStickers": 216,
  // ... other scalars ...
  "blocks": {
    "stickerCenters": {
      "offset": 4096,      // byte position where this block starts
      "length": 6912,      // how many bytes it occupies
      "dtype": "f64",      // 64-bit floats
      "shape": [216, 4]    // 216 stickers x 4 coordinates
    },
    "sticker2face": { "offset": 11008, "length": 432, "dtype": "u16", "shape": [216] }
    // ... ~20 more ...
  }
}
```

**Offset** is simply a byte position measured from the start of the file — "this array's bytes begin
4,096 bytes in." The decoder reads it and does:

```ts
new Float64Array(buffer, 4096, 864)   // 864 doubles = 6912 bytes
```

That is a **view**: a typed array pointing at bytes already in memory, not a copy of them. Writing
through it would write into the file's buffer. This is what makes loading nearly free — the file *is*
the in-memory representation, and the block table is just the map.

`dtype` is one of `f32`, `f64`, `u8`, `u16`, `u32`, `i32`, and it is chosen per block: see
[precision](#precision-f32-vs-f64) below. `shape` is informational — it says how to read the flat
run of numbers as rows.

---

## Alignment

Every block starts at a byte offset that is a multiple of 8, with zero padding inserted as needed.

This is not tidiness, it is a hard JavaScript constraint. A typed array can only be created at a byte
offset that is a multiple of its element size:

```ts
new Float64Array(buffer, 4096, 864)   // fine: 4096 = 512 x 8
new Float64Array(buffer, 4100, 864)   // RangeError: start offset must be a multiple of 8
```

Eight bytes is the largest element the format uses, so aligning everything to 8 makes every block
legal regardless of its type.

> **This bites in Node, too.** `readFileSync` returns a `Buffer` backed by a *pooled* `ArrayBuffer`,
> so its `byteOffset` is essentially never a multiple of 8 — and building `Float64Array` views over
> it throws. The fixture loader in the test suite copies into a fresh `ArrayBuffer` first. Anyone
> doing zero-copy binary work in Node will hit this.

## Why the offsets are computed iteratively

There is a circularity in writing this file, and it is worth recording because the first
implementation got it wrong.

The block table has to contain each block's offset. But the offsets depend on where the blocks
start, which depends on how long the header is — and the header's length depends on the offsets,
because a bigger number is more characters. Writing `"offset": 1048576` instead of `"offset": 0`
makes the header seven bytes longer, which pushes every block seven bytes further out, which can
make the offsets longer still.

The fix is to iterate to a fixpoint: lay the blocks out against the current header length, re-render
the header, and repeat until it stops growing. Each round only ever adds digits, so it converges in
two or three passes. The header is then space-padded to the reserved length, which keeps the layout
valid if the final render came out slightly shorter — trailing spaces being legal JSON whitespace.

The first attempt instead laid out against a header with all offsets still zero and asserted the
real header would fit. It never does.

## Precision: f32 vs f64

The choice of `dtype` per block is not a size optimisation. It is load-bearing.

**Render-path data is f32** — vertex offsets, face centres, grip centres. The original narrows these
to Java `float` itself, so f32 here is *bit-exact* with the original rather than an approximation.

**Twist-path data is f64, and must be.** `stickerCenters`, `faceInwardNormals`, `faceCutOffsets`, and
`gripUsefulMats` feed the spatial hash that turns a rotated sticker centre back into a sticker index.
That hash uses **absolute** epsilons of 1e-9 and 1e-8, and the catalog reaches a circumradius of
31.87 — making the tolerance 3.1e-10 relative, roughly 380× finer than float32 resolves.

Narrowing any of those four would break twisting, but only on large-coordinate puzzles and only for
some grips: a silent, data-dependent failure. The test suite's canary is a property test asserting
that every twist permutation is a bijection, which fails immediately and names the puzzle and grip.

## What the blocks contain

| Block | Type | Shape | Purpose |
|---|---|---|---|
| `vertsMinusStickerCenters` | f32 | nVerts × 4 | each vertex's offset from its own sticker's centre |
| `stickerCenterMinusFaceCenter` | f32 | nStickers × 4 | each sticker centre's offset from its face centre |
| `faceCenters` | f32 | nFaces × 4 | face centres |
| `stickerVertBegin` / `stickerVertCount` | u32 / u16 | nStickers | each sticker's contiguous vertex range |
| `stickerPolyCount` | u16 | nStickers | polygons per sticker |
| `polyVertCount` | u8 | nPolys | vertices per polygon |
| `polyIndsLocal` | u8 | — | polygon vertex indices, *relative to the owning sticker* |
| `sticker2face` | u16 | nStickers | which face each sticker belongs to; also the solved state |
| `sticker2cubie` | u32 | nStickers | which physical piece; values are union-find roots, so non-consecutive |
| `face2OppositeFace` | i32 | nFaces | −1 where there is none, as on a simplex |
| `stickerCenters` | **f64** | nStickers × 4 | the twist lookup key |
| `faceInwardNormals` | **f64** | nFaces × 4 | slice classification |
| `faceCutCounts` / `faceCutOffsets` | u8 / **f64** | ragged | where the cut hyperplanes sit |
| `gripUsefulMats` | **f64** | nGrips × 4 × 4 | each grip's orthonormal rotation basis |
| `gripCenters` | f32 | nGrips × 4 | for nearest-grip picking |
| `gripDims` | u8 | nGrips | 0 = vertex grip, 1 = edge, 2 = face, 3 = cell centre |
| `grip2face` | u16 | nGrips | which cell a grip belongs to |
| `gripSymmetryOrders` | u16 | nGrips | twist angle is 2π/order; 0 = cannot rotate, 1 = no-op |
| `nicePoints` | f32 | — | snap targets for "rotate this to the centre" |

### The three shrink arrays

The original keeps three parallel per-vertex arrays and recombines them each frame to apply the
face-shrink and sticker-shrink sliders:

```
vertex = (vertMinusStickerCenter · stickerShrink + stickerCentreMinusFaceCentre) · faceShrink
         + faceCentre
```

Two of those three are **aliases** — one `float[]` shared by every vertex of a sticker, and one
shared by every vertex of a face. Storing them at their true cardinality is lossless and cuts the
dominant term by roughly a factor of three.

### Sticker-local polygon indices

In 4D the original builds each sticker's geometry independently and concatenates the results, so
there is no vertex sharing between stickers: **each sticker owns a private, contiguous vertex
range**. Polygon indices are therefore stored relative to `stickerVertBegin`, which fits them in a
single byte.

The exporter asserts this rather than assuming it — that the ranges are contiguous, in order, and
cover every vertex. Largest range in the whole catalog is 200, comfortably under 256.

## Sizes

Measured over all 128 catalog entries:

| | Raw | Gzipped |
|---|---|---|
| `{4,3,3} 3` (the default puzzle) | 81 KB | **8.2 KB** |
| `{5,3,3} 2` (the largest) | 2.79 MB | 805 KB |
| Whole catalog | 56.9 MB | — |

Assets are lazy-loaded per puzzle, so the number that matters is the 8 KB default. Gzip does
unusually well here because the hypercube is highly symmetric and its float data repeats.

Files are served pre-gzipped and inflated with `DecompressionStream`, which is baseline in current
browsers.

## Stability

**Grip indices in these assets are a wire format.** Every move in every MagicCube4D `.log` file ever
saved is an index into the grip array, so regenerating assets with a different exporter or a
different JDK could silently invalidate every saved solve in existence.

Accordingly:

- the exporter pins its JDK version,
- `manifest.json` records a sha256 per asset and is committed,
- CI regenerates and fails on any hash change without an explicit `assetsVersion` bump,
- every save file records the `assetsVersion` it was created against.

The whole catalog rebuilds in about 18 seconds, so that check is cheap enough to run on every pull
request.

## Header reference

```
offset 0   "MC4DPZ\0"          7 bytes
offset 7   version             u8, currently 1
offset 8   headerLength        u32, little-endian
offset 12  header              JSON, UTF-8, space-padded to headerLength
           ...padding to the next multiple of 8...
           blocks, each padded to start on a multiple of 8
```

Everything is little-endian, which every platform this targets is natively.
